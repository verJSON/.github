## Context

The organization ruleset `ai-authorization-arm-required` (20722935) has one
`workflows` rule. It requires `.github/workflows/gate-rearm.yml` from
`verJSON/.github`, pinned to `24db445f`, on every repository selected by
`verjson-core-checks=enforced`. The repository-local `gate re-arm` caller is
generated by `scripts/gen-gate-rearm-caller.sh`. It has the same path and the same
head triggers, and it shares the `ai-review-arm-<PR>` concurrency group with the
required run. GitHub keeps one pending run per group, so the local run can
displace the required one. The required run is then cancelled, and the `workflows`
rule blocks the merge. #1905 records the shape on verjson-temporal-kit#210 and #223.
It recurred on 2026-11-03 on verJSON/verjson-identity-contracts#121, head
`3b001575`. Required run 41703191233 was cancelled 2 s after creation. Local
run 41703192236 succeeded.

`scripts/assert-mergeable-head.sh` printed `true` for that head. Gate A reads only
`required_status_checks`. The 2026-10-15 ADR 0226 amendment sets aside exactly
this cancelled run as a family displacement. The required run had created no job,
so Gates A and C saw nothing red. The gate exited 0 while GitHub refused the
merge. `gh run rerun` on a required run answers 404, so close-and-reopen is the
only re-trigger.

The Architecture Review Board ran Charter F on #1905 (ARB RUN-F, 3 rounds, slate
revision 3, digest `a11e1589…`). It ended `CHANGES_REQUESTED / ESCALATE`. F-3 and
F-6 were unanimous, F-4 and F-9 passed 2-1, and F-1 failed 0-3. On 2026-11-03 the
owner partially ratified it as decision `ARB-F-RUN-F-2026-11-03`. The decision was
relayed to the chair by the coordinating agent, and the owner's identity was not
independently verified. Tranche 1 ships F-3, F-4, F-6, and F-9, with the three
"never cancel" exceptions. F-1, the event-time guard, ships later. F-2 and F-7,
the group split, stay deferred until a fencing primitive is proven. F-5 was not
addressed. This ADR records tranche 1. Members' dissent is preserved in the run
ledger (`round3-ratified.json`) and is not restated here.

## Decision

### 1. Gate W (F-4)

`assert-mergeable-head.sh` gains **Gate W**, evaluated after Gate A. For each
required-workflow entry of every `type: workflows` rule returned by
`repos/{o}/{r}/rules/branches/{base}`, the head must carry a qualifying run.

- **Binding uses provider fields only.** A run binds to the entry only when all
  of these hold:
  - its `path` equals the entry's path;
  - its `event` is `pull_request_target`;
  - its `head_sha` is the exact head (the run inventory admits nothing else);
  - its `workflow_url` ends in `/actions/required_workflows/<its own workflow_id>`,
    which a repository cannot forge;
  - its head branch and head repository are this pull request's.

  The last is the closest PR binding GitHub exposes, because `pull_requests` is
  empty on these runs. It rejects a reused branch name or another fork on the
  same SHA. The run name is never read, because a caller chooses it.

  The `pull_request_target` event is a property of the required workflow that
  ruleset 20722935 requires today, not of `workflows` rules in general. A future
  required workflow triggered by another event, such as `pull_request` or
  `merge_group`, would read as `unbound` and fail closed until Gate W learns the
  event that workflow is triggered by.
- **Freshness (owner timing rule).** A bound run counts only if it was created
  strictly after the `updated_at` of its ruleset. Gate W reads that time from
  `repos/{o}/{r}/rulesets/{id}`, which needs only repository read: it answered an
  unauthenticated caller for `verJSON/.github` on 2026-11-03. A run created in
  the same second counts as stale. The endpoint returns both `…Z` and `…-05:00`
  forms, and both are parsed.

  **Assumption: GitHub truncates a run's `created_at` to the second, and never
  rounds it.** Under truncation, a run reported at the change's second may have
  been created before the change, so treating it as stale is correct. If GitHub
  rounded up instead, a run created up to half a second before the change could
  report the next second and read as fresh. No provider documentation states
  which applies. A second-granular timestamp gives no way to verify it.

  **Assumption: minimum grant on private repositories.** On 2026-11-03 the
  rulesets endpoint returned `updated_at` and `rules` for ruleset 20722935
  through both the public `verJSON/.github` (no authentication) and the private
  `verJSON/verjson-identity-contracts` and `verJSON/verjson-oidc-claims-middleware`.
  For the private repositories, the token was a classic OAuth token carrying
  `repo` and `admin:org`. That proves the response shape. It does not prove that
  a fine-grained token with only Metadata (read), or an Actions `GITHUB_TOKEN`
  with `contents: read`, receives the same response. Gate W assumes it does. A
  refusal exits 1 and names the grant. A body without a readable `updated_at`
  fails closed as `undated`. Either way, a wrong assumption costs liveness, never
  safety.
- **The verdict is the newest fresh run** of the bound required workflow, ordered
  by `run_number`. It must have completed with `success`. A cancelled required
  run is superseded only by a later successful run of the **same** required
  workflow on the exact head. An older success does not rescue a newer cancelled
  run.
- **The ADR 0226 family set-aside never satisfies Gate W.** It still dismisses the
  cancelled check for Gates A and C. Gate W reads the raw run inventory, not the
  gated check inventory.
- **Every unanswerable case fails closed with exit 3**, under one named reason:
  - `absent` — no required-workflow run at the path; a local run at that path
    is not one;
  - `unbound` — such runs exist, but none binds;
  - `stale`;
  - `undated` — the ruleset or a bound run has no readable time;
  - `ambiguous` — fresh runs of more than one required-workflow id share the
    path, or the rules name one path twice, since a run reports no source
    repository. This includes identical entries carried by two different
    rulesets on the same ref: they fail closed even though either run would
    satisfy both;
  - `changed` — the ruleset read no longer carries the entry the branch rules
    returned;
  - `cancelled`;
  - `not successful`;
  - a rule shape Gate W cannot read (a missing `ruleset_id`, a missing or empty
    `parameters.workflows`, or an entry without a path). This is never the
    vacuous pass.

  A refused or foreign ruleset response exits 1, as every unreadable inventory
  does.
- **A ref with no `workflows` rule leaves Gate W vacuous.** GitHub requires nothing
  there either. The 2026-11-03 readback confirms that `rules/branches/{base}`
  returns the organization's `workflows` rule, with its `ruleset_id`, to a
  repository-read caller. That was the platform-unverified canary premise of F-4.
- **Exit code: Gate W uses exit 3.** It joins Gate A's "required evidence for the
  base ref is not satisfied" code instead of taking a new one, and the message
  names `Gate W:`. The ratified F-4 acceptance specifies exit 3. A new code would
  change the exit contract ADR 0184 fixed, and with it every caller that branches
  on it. The trade-off: automation that wants to route Gate W's remedy separately
  from Gate A's must read the message prefix.

Gate W is a **precondition only**. It does not prove event binding, PR identity, or
scheduling under the currently pinned SHA: a required run reports
`referenced_workflows: []`. The timing rule bounds that gap but does not close it.
It is never AI-authorization evidence. The `arm` and watchdog jobs are
`continue-on-error`, so a successful required run does not show that the arm
succeeded. Merge admission authority and its evidence stay with #1945. Gate W
tightens the gate and relaxes nothing.

### 2. Every ruleset edit ships a re-arm sweep (timing rule)

`updated_at` moves on any edit to the ruleset, not only on a pin rotation. Each
edit therefore makes Gate W refuse, as `stale`, every open enrolled pull request
whose required run predates it. The owner accepted that cost to fail closed. Every
change that edits a ruleset carrying a `workflows` rule ships a planned re-arm
sweep. The sweep lists the targeted repositories, classifies open pull requests
with the read-only assertion, and records each edit in the runbook's sweep
checklist. A `stale` head is re-armed **per pull request, at merge time**, by
whoever owns that pull request, under the rules in §4. Then the new run is
verified. The sweep is never a mass close-and-reopen across other sessions' pull
requests. A bulk reopen would also re-create the concurrency pile-up that §4's
quiet-family rule exists to avoid. The procedure and the checklist are in
[`docs/arm-recovery-runbook.md`](../../arm-recovery-runbook.md#re-arm-sweep-after-a-ruleset-edit).
The sweep is this ADR's own scope, recorded here and in the checklist rather
than in a separate issue.

### 3. The required workflow never skips or yields (F-3)

The required run always performs the arm for `opened`, `reopened`, and
`synchronize`. It never skips or yields because a local caller ran. A yielding
required run would satisfy ruleset 20722935 without an organization-controlled
arm, while the local run's claim is controlled by the repository. On the
required path, no job or step condition reads the invocation's identity. The
arm's `WORKFLOW_REF` classification recognizes only the label and lifecycle
callers, so the required run and the head caller take the same path. A contract
test pins both.

The arm's existing duplicate-authorization no-op (`gate-rearm.yml`, "duplicate
event is a no-op") is unchanged. It is a non-atomic read-then-create over the
authorization check, which the board recorded as a chair-verified fact. Its
mutual exclusion belongs to F-2 and #1945. It is not a yield of the run: the
required run still executes its jobs and concludes on its own.

### 4. Interim recovery: close and reopen (F-6)

When the newest required run on the exact head is cancelled, the recovery is a
close-and-reopen of the pull request, under these rules:

- **Actor.** Only a human, or an App identity whose events start workflows. Never
  `GITHUB_TOKEN`, whose events start none.
- **Quiet family.** Act only when the PR-wide arm family is quiet: no queued or
  in-progress run of the required arm, `gate re-arm`, `AI review label re-arm`, or
  `AI review lifecycle re-arm`, across heads and pins. The PR number is
  unobservable on these runs, so the family is bound by head branch and head
  repository. If quiet cannot be established, stop and escalate. The check is not
  atomic: recheck it after each attempt.
- **Cap.** At most 2 attempts per head, then stop and escalate.
- **Verify.** After each attempt, confirm a new exact-head required run concluded
  `success`, and that Gate W and the admission evidence pass.
- **Side effects.** Re-request auto-merge if closing cleared it. Reopen a
  Renovate-authored pull request immediately. If Renovate posted an ignore notice,
  recreate the pull request through the dependency dashboard.
- **Never** `gh run rerun`, which answers 404 for a required workflow. **Never**
  an admin bypass.

Its use against concurrency displacement is interim. It ends when F-1, Gate W, and
the F-7 closure are verified fleet-wide. The same actor, cap, quiet-family, and
never-rerun rules remain **permanently** for watchdog and external cancellations.
*(Amended 2026-11-06: F-1 here reads F-1R; see the amendment below.)*

### 5. The three "never cancel" exceptions (owner-ratified)

"Never cancel the required run" means **no concurrency displacement by a
non-required run**. Three cancellations are outside that guarantee:

1. the runner-acquisition watchdog's own cancellation (ADR 0230);
2. an external cancellation, by an operator or by the platform;
3. one required run replacing another required run of the same pull request,
   including a run for an older head.

Each costs liveness, never safety, because Gate W fails closed on the cancelled
run until a later run of the same required workflow succeeds. Exception 3 is the
one board member codex asked the owner to ratify explicitly, and the owner did.

### 6. Watchdog recovery advice per invocation kind (F-9)

The watchdog's message stops advising a re-run that cannot work. It names the
recovery for the kind of run it cancelled:

- **required run** (a direct invocation): close and reopen the pull request
  under §4, or push. It cannot be re-run.
- **caller head run** (the local `gate re-arm`): re-run that run, or push.
  *(Amended 2026-11-06: push a new head, or re-run only where the base ref
  requires no organization arm; see the amendment below.)*
- **label or lifecycle delivery**: the delivery refuses a second attempt.
  Re-deliver the event instead: remove and re-apply the label, or repeat the
  lifecycle transition.

Recovery is described as possible, never assured. It depends on §4's quiet check
and on verified new required-run evidence.

## Alternatives rejected

- **A new exit code for Gate W.** Rejected for the reasons in §1, and because the
  ratified acceptance names exit 3.
- **Ambiguity across every run on the head, stale ones included.** A
  required-workflow id seen only before the ruleset changed is no candidate for
  the current rule. Counting it would make a same-head re-arm after a
  re-registration permanently ambiguous. A stale run never satisfies Gate W in
  either design. The risk left over: one branch opened as pull requests against
  two bases whose rulesets require the same path. Those runs carry the same head
  branch, repository and SHA, so either run binds to both pull requests. That is
  the F-4(4) PR-identity limit, because no run field reports the pull-request
  number.
- **Binding by run name.** A caller chooses the name, as `gate re-arm` does.
- **Letting the family displacement satisfy Gate W.** That is the #1905 hole
  itself: a repository-controlled run standing in for the organization's.
- **Reading the required run's check runs.** A run cancelled before it created a
  job leaves no check, which was the live #121 shape.
- **A yielding required workflow, or a local caller that skips.** Rejected by F-3
  (§3). F-1, the event-time guard in the local caller, ships separately with
  enroll-first order.
  *(Amended 2026-11-06: F-3 rejected a yielding required run; F-1R's liveness
  skip of the non-required head-event arm is adopted; see the amendment below.)*

## Consequences

- Gate W takes effect wherever an adopter runs the canonical script from `main`
  (`rules/workflow.md` → *Pull Requests*). No caller pin moves.
- The ruleset was edited at 2026-11-03T16:39:01Z. Every open enrolled pull request
  whose required run predates that is `stale` until it is re-armed. That edit is
  the first entry in the runbook's sweep checklist. Its known stale heads at
  recording time are re-armed per pull request at merge time, not in bulk.
- The F-9 message reaches consumers only when the ruleset pin is rotated past this
  commit, and through regenerated caller pins. Rotating the pin is itself a
  ruleset edit, so it ships with a sweep (§2).
- The duplicate-authorization no-op, the group split (F-2/F-7), and the
  event-time guard (F-1) are untouched.
  *(Amended 2026-11-06: the guard ships as F-1R; see the amendment below.)*

## Amendment (2026-11-06) — F-1R: the local caller yields to the required arm

### Context

ARB decision ARB-G1-2026-11-06, candidate C1, replaced F-1 with F-1R:
`ADOPTED_WITH_CONSTRAINTS`, 3-0, final slate revision 3, digest
`ba9aada5c945eb8f…` ([#1905 comment](https://github.com/verJSON/.github/issues/1905#issuecomment-6691352431)).
F-1 had failed 0-3 in RUN-F. All three identity-verified members judged that F-1R
answers that dissent: the guard carries no admission authority, and an uncertain
read keeps the behavior before this amendment. The repository owner delegated
ratification to the board on 2026-11-06. The board recorded two gaps: the RUN-F
ledger was not found, so members reconstructed its dissent from this ADR and
#1905, and the organization context came from the unmerged verjson-docs#20.

### Decision

1. **The generated caller gains a `guard` job.** `scripts/gen-gate-rearm-caller.sh`
   emits a `guard` job ahead of `rearm`. The guard has a read-only token
   (`contents: read`) and no concurrency. `rearm` has `needs: guard` and runs only
   when the guard outputs `local_arm=true`. The caller declares no workflow-level
   concurrency. The `ai-review-arm-<PR>` group is declared by the reusable workflow
   and engages only when `rearm` starts, so a skipped `rearm` cannot displace the
   pending required run.
2. **The guard yields only on positive evidence.** It reads
   `repos/{owner}/{repo}/rules/branches/{base}` only for `pull_request_target`
   `opened`, `reopened`, and `synchronize`. It outputs `local_arm=false` only when
   the response meets all of these conditions:
   - it is a JSON array of objects;
   - every `workflows` rule has a numeric `ruleset_id` and a non-empty list of
     entries, each with a string `path` and a numeric `repository_id`;
   - an entry names `.github/workflows/gate-rearm.yml` from repository
     `1269388380`;
   - no entry at that path names another repository. A run reports its path but
     not its source repository, so a shared path is ambiguous.

   Any other outcome outputs `local_arm=true`, the behavior before this amendment.
   That includes another event or action, a read error, and a body that is not
   JSON or not an array. Every decision logs its reason. A step failure also
   yields `true`: the step has `continue-on-error`, and the job output maps
   anything but `false` to `true`. The `workflow_call` path that the label and
   lifecycle callers use keeps its local arm.
   GitHub's REST reference says this endpoint does not return rules from rulesets
   in `evaluate` or `disabled` enforcement (read 2026-11-06). The response
   carries no enforcement field, so the guard has nothing to check there. The
   live `verJSON/verjson-ai` response read on 2026-11-06 has the fields above.
   The logic is `scripts/local-arm-guard.sh`, which the generator embeds
   byte for byte.
3. **The guard is never admission evidence.** Gate W (§1) remains the only
   required-run check, and it fails closed. A wrong guard decision costs liveness,
   which §4 recovers, never safety.
4. **No ruleset pin rotation.** Only regenerated callers change. These
   preconditions apply before fleet regeneration:
   - the generator contract test, with every assertion mutation-proven (met);
   - the live canaries (a), (b), and (c) that the decision specifies (not yet
     run);
   - the per-reason Gate W remedy (met by #2010, which landed before this
     amendment);
   - this amendment (met);
   - the `assert-mergeable-head` fixture below (met).
5. **The residual risk stays recorded.** F-2 and F-7 remain deferred: label and
   lifecycle runs can still displace a pending required run. F-6 close-and-reopen
   remains interim. F-1R adds two residuals:
   - A `guard` job that never acquires a runner leaves `rearm` skipped. This costs
     the local arm on a base ref with no organization arm. The required run is
     unaffected.
   - A guard-skipped `gate re-arm` run still matches the declared family's caller
     list, although it never entered the group. ADR 0226's displacer consults
     only the newest later-created family run and needs a SUCCESS-only suite. So
     a displaced family run followed by a guard-skipped local run (`guard`
     SUCCESS, `rearm` SKIPPED) is not set aside. The assertion exits `5` on Gate
     C, naming the displaced check (`rearm / event-policy=CANCELLED`), and gives
     no recovery text. Gate W is satisfied by the required run. To recover,
     re-deliver the displaced event as §6 describes. A later successful run of
     that workflow sets the cancelled check aside under ADR 0226's same-workflow
     rule. A new head also recovers. A change that stops the family rule from
     consulting a run whose arm job was skipped is a Gate C admission change,
     outside this decision.

### Reconciliation with this ADR's own text

- **Rejected alternatives, "a local caller that skips".** F-3 rejected a
  *yielding required run*: a run that satisfies ruleset 20722935 without an
  organization-controlled arm. §3 is unchanged, and the required run still never
  skips or yields. F-1R is a liveness skip of the *non-required* head-event arm.
  It happens only where the base ref already requires the organization's arm,
  which is the enroll-first order this ADR named.
- **§4, "It ends when F-1, Gate W, and the F-7 closure are verified
  fleet-wide".** F-1 now reads F-1R. Close-and-reopen remains interim until F-1R
  is regenerated fleet-wide after the canaries and F-7 closes.
- **§6, caller head run.** "Re-run that run, or push" contradicted the runbook's
  never-rerun rule (#2047). A re-run joins `ai-review-arm-<PR>` outside the
  quiet-family check and can displace a pending required run. Under F-1R, a
  caller head run reaches the arm only when the guard kept the local arm. That
  happens on a base ref with no organization arm, where a re-run is safe, or
  after an uncertain read on one that has the arm, where a re-run is not safe.
  The watchdog now advises pushing a new head, or re-running only where the
  base ref requires no organization arm (`.github/workflows/gate-rearm.yml`).
- **Consequences, "the event-time guard (F-1) [is] untouched".** It ships as
  F-1R in the generator. Adopters receive it only through regenerated callers.

### Verification

- `scripts/ci-gate/local-arm-guard.test.py` (merge-gate group) runs the helper
  under Actions' `bash -eo pipefail` against a stubbed `gh`. It covers each
  `true`/`false` outcome above with its logged reason, the encoded
  single-segment base ref, a later page, and an injected workflow command in a
  read error.
- `scripts/ci-gate/gate-rearm-caller-contract.test.sh` pins these properties:
  - the `guard`, `needs`, and `if` shape;
  - the guard's read-only grant and its normalized output;
  - the embedded helper bytes;
  - no concurrency at the workflow or job level.
- Mutations were killed: 12 against the helper and 10 against the generator.
- `scripts/assert-mergeable-head.required-workflow.test.sh` records the
  displaced-family-run verdict above. A mutation that lets the displacer accept
  a SKIPPED check makes that test fail.
- Not verified here: the live canaries, and two GitHub behaviors the fixture
  assumes. The fixture assumes that a run whose reusable-call job was skipped
  still lists its `referenced_workflows`, and that the skipped job reports one
  check run named `rearm`. Canary (a) observes both.
