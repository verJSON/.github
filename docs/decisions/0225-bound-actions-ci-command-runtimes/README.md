# 0225 — Bound actions-ci command runtimes

- **Date:** 2026-10-09
- **Status:** Accepted
- **Issue:** [verJSON/.github#1736](https://github.com/verJSON/.github/issues/1736)
- **Extends:** [ADR 0076](../0076-bounded-actions-ci-shell-test-groups/README.md)
- **Extends:** [ADR 0224](../0224-shard-changelog-release-actions-ci/README.md)
- **Category:** CI policy

## Context

ADR 0224 split the changelog-release group into four matrix cells and assigned each caller-contract case to exactly one cell. Each case still ran the full generated contract, and every shard repeated generator-wide setup and assertions. The remaining manifest commands also ran serially. In run [37874848459](https://github.com/VerJSON/.github/actions/runs/37874848459), the affected commands ranged from 71 to 202 seconds, while `platform` and `merge-gate` occupied their runners for 13m 20s and 9m 49s.

The 60-second command budget requires reducing each command's work while preserving every assertion. ADR 0224 already partitions caller mutations across four matrix cells, and requires every mutation to run the complete generated contract. Issue #1743 records that those four multi-case commands still take four to five minutes, and asks whether to keep cutting them. The remaining manifest commands also repeat workflow parsing, generated-caller construction, and per-file scans. The four cells and six-job concurrency provide the available runner capacity; adding hosted jobs would repeat checkout and setup. The first full run also showed that CPU-heavy rows could exceed the budget while competing with sibling rows.

The first draft of this decision gave each caller-contract case its own manifest row, 233 rows in all. Run [38014446043](https://github.com/verJSON/.github/actions/runs/38014446043) rejected that. Every caller-contract process walks the fixture construction for all 233 cases before running its own, so a one-case row took about 50 seconds on a 2-vCPU general runner. Each cell queued about 58 such rows and approached or reached the 30-minute job timeout. The same run measured several `platform` and `merge-gate` rows at 45 to 56 seconds, and one exclusive row above 60 seconds. On developer hardware, the manifest contract took 10 seconds and the generator-only caller-contract row 8 seconds, against 60 or more and 54 seconds on CI. A single 60-second budget calibrated on that hardware therefore failed on CI for reasons unrelated to regressions. In the same run, the one-case shards also exposed a fixture leak: shards skipped the capture of the custom-release contract suite, wrote an empty suite, and accepted mutations the full run rejects.

## Decision

1. Run independent actions-ci manifest rows concurrently up to the runner's available CPUs. Count them with `nproc`, reduced to the cgroup v2 `cpu.max` quota (rounded up) when the quota is lower. Export the count as `ACTIONS_CI_AVAILABLE_CPUS` for rows that schedule their own workers. `ACTIONS_CI_COMMAND_PARALLELISM` overrides it to reproduce CI contention locally. Only the cgroup v2 `cpu.max` interface is read; on a cgroup v1 host the count falls back to `nproc`. An `@exclusive` row waits for active siblings and completes before the next row starts, reserving the full runner for commands that otherwise time out under contention. Buffer each row's output and emit its output, status, and elapsed time as soon as that worker is reaped, so a hanging sibling cannot hide completed diagnostics. Report the group result after all rows finish.
2. Enforce `ACTIONS_CI_COMMAND_BUDGET_SECONDS=60` on every pull-request invocation of the group runner, including the documentation-contract job, as the default row budget. The default covers rows measured at 30 seconds or less on the general runners, a margin of at least 2x. A row measured above 30 seconds declares `@budget=<seconds>` in the manifest, after any `@exclusive`. The value is twice its slowest CI measurement, rounded up to 30 seconds, and may not exceed 600 seconds. `scripts/actions-ci-groups.test.sh` pins every declaration, so raising a budget requires review. Declared budgets apply only when the group budget is enabled. The runner itself rejects a budget above 600 seconds and any row without exactly two tab-separated fields. Row budgets do not bound a group's total; the 30-minute job timeout remains the group-level bound and still fails the job closed. Keep the push-to-`main` ShellCheck audit over the full tracked tree; pull requests check changed tracked shell scripts.
3. Cache parsed workflow inputs, generated-caller output, and per-file logical-line scans where a command repeats that work. Keep each cache inside the command that fills it, and hand callers copies rather than a shared mutable parse. A cache shared across rows existed only to amortize the rejected one-row-per-case layout, and it was removed with that layout.
4. Keep ADR 0224's four caller-contract shards, one per changelog-release cell, as the first rows of their cells. Each shard schedules its cases across `ACTIONS_CI_AVAILABLE_CPUS` and declares `@budget=600`, twice the slowest shard measured in #1743 (5m00s). Run the generator-wide assertions once in a separate `@budget=120` row rather than in every shard. Every case fixture is built before the generator-only section, and the captures have no empty default, so a fixture a shard skips aborts under `set -u`. A generator mode that exits 0 with no output fails its capture. Retain `max-parallel: 6`, and run the complete generated contract for every selected mutation. Do not add a section selector or skip assertions for any mutation.
5. Keep the `platform` and `merge-gate` jobs and the required `shell-tests` context unchanged. Do not add hosted runner jobs for these shards.

## Consequences

Every caller mutation still runs exactly once with the full generated assertions. Every caller-contract run makes exactly 268 case selections, the number pinned in `scripts/changelog-caller-contract-shard.sh`. The caller fails in every shard, with assertions unsuspended, if that count drifts. The shard test checks that the helper partitions those selections across the four shards, within one of each other. It also checks that the manifest carries exactly one budgeted shard per cell plus the generator-only row. A static check fails if a case reads a fixture that only the generator-only section defines. Generator-wide checks run in their own command row. This settles #1743: the caller-contract rows stay above 60 seconds under a declared budget. Cutting them further would multiply the per-process fixture walk faster than it reduces per-row work. The required-checks audit, conformance suite, actions-ci manifest contract, and privileged-merge conformance rows are marked `@exclusive`; all other independent rows run at the available-CPU parallelism. Each row's report line names the budget it ran under. The audit contract suite divides its cases into two isolated partitions and runs them concurrently within one exclusive row, preserving every assertion while avoiding sibling-row contention. The effective parallelism and command count are logged. Each command runs in an isolated process group; budgeted commands use `timeout --foreground` so descendants stay in that tracked group. Output is captured to a per-command file and sanitized after the process exits, so a descendant inheriting stdout cannot keep the supervisor blocked. Surviving descendants are terminated and reported, timeouts stop the full command group, and cancellation waits for workers to clean up before removing shared temporary data. If a worker dies before sanitizing output, the parent sanitizes and reports its raw log before removing scratch data. Each worker's output, status, and elapsed time are emitted when it is reaped, so completed diagnostics remain visible if another row hangs or the job is interrupted. Missing or malformed worker results fail the group instead of reusing stale status. Commands run with stdin from `/dev/null`, and the runner reads the manifest on its own descriptor. The group also fails unless the number of rows it started and reported equals the number of rows the manifest selects for that group, so a row dropped by any early exit is a failure rather than a pass. The pull-request command budget makes duration regressions fail at the affected row; the `main` full-tree ShellCheck audit remains uncapped so its complete scan stays enabled.

Amendment (2026-10-14, #1767): rows start asynchronously, and a non-interactive bash gives asynchronous commands SIGINT and SIGQUIT ignored. The supervisor therefore execs each row through `env --default-signal=INT,QUIT` on both the budgeted and the unbudgeted path. It does not rely on `timeout` restoring them, because push runs on `main` have no budget. The runner refuses to start without that `env` option.

Measure the next `actions-ci` run against the issue's eight-minute `platform` and `merge-gate` targets, the 60-second default, and each declared budget. Lower a declaration that runs well under half its budget, and declare one for a row that drifts above 30 seconds. Rollback can remove command-level parallelism, the budget, and the repeated-work caches while keeping the four-cell changelog-release split from ADR 0224.

Amendment (2026-10-17, [verjson-observability#271](https://github.com/Verjson/verjson-observability/issues/271) slice 4): the row line `actions-ci command group=<g> status=<n> elapsed=<s>s budget=<s>s command=<cmd>` is now an input to the pull-based runtime collector (verjson-observability#272), so it must be authoritative. Scratch run [Verjson/demo-repository 39064216676](https://github.com/Verjson/demo-repository/actions/runs/39064216676) showed three ways replayed output could hide or forge it: (a) output ending in `##[endgroup]` without a newline is stored as a bare group end and the next producer line is lost; (b) the runner trims leading whitespace, so ` ::add-mask::command group=` masks every later row for the rest of the job; (c) inside `::stop-commands::` a forged `##[endgroup]` is stored byte-identical to a real one. The runner reads output with .NET `ReadLine`, so a bare carriage return also starts a stored line.

1. **Replay.** Each row's output is replayed between `::stop-commands::<token>` and `::<token>::`. The token is 128 bits from `/dev/urandom`, drawn by the runner after the row exited, so nothing the row printed can contain it; if no token can be drawn the output is withheld and the row fails. Every replayed line, and every segment after a bare carriage return, is prefixed with `| `, and awk terminates the last line, so no stored line of command output can begin with `::`, `##[`, or the row text. The sanitizer also rewrites indented workflow commands and redacts an indented add-mask's value. Every `::error::` and row line is preceded by a newline as a second layer. The row line's format is unchanged. **Consumer contract:** the prefix guarantee holds for the line ends the Actions runner honors, LF and bare CR, and the replay deliberately does not prefix after other separators. A consumer of the stored log must therefore split on LF only, tolerating a trailing CR, and must require the runner's timestamp prefix (`YYYY-MM-DDTHH:MM:SS.fffffffZ `) on every producer line it accepts. A consumer that also splits on VT, FF, NEL, LS, PS, or FS/GS/RS (Python `str.splitlines()`, for example) can see a forged row at column 0. verjson-observability#272 already anchors on the exact timestamp prefix. `scripts/actions-ci-group-records.test.sh` pins that a row forged after each of those separators stays inside a prefixed LF line.
2. **Records.** When `ACTIONS_CI_RUNTIME_RECORDS` names an absolute path, the runner unsets the variable before any row starts and, after each row is reaped, rewrites that file from its own memory as JSON Lines, one record per row in manifest order (`schema_version` 1: `group`, `command`, `status`, `elapsed_seconds`, `budget_seconds`, `started_at`, `ended_at`, `timed_out`, `left_background`, `runner_name`, `runner_environment`). A row without a usable worker result is recorded with the row line's `"missing"` or `"invalid"` status and null result fields. Each rewrite is staged through `mktemp` under an unpredictable name and renamed into place, so a row cannot redirect it with a planted symlink. A relative path is a configuration bug and exits 2 before any row runs. A path that cannot be created, or a file that can no longer be rewritten, produces one `::warning::` naming the path, and the rows alone decide the group result: merges must not depend on telemetry disk I/O, and the collector fails closed on a record-count mismatch (item 3), so a missing record cannot read as "nothing to report". `shell-test-groups` points the variable at `runner.temp/actions-ci-runtime-records-<run_id>-<attempt>/<group>.jsonl`, outside the checkout copy the step deletes and keyed like that copy against reused self-hosted temp directories. It uploads each cell's file with `if: always()` as a seven-day artifact named per run, attempt, and cell. The `docs` and `locale-collation` groups run without the variable and produce no records, so consumers must not expect them.
3. **Integrity, honestly bounded.** A row runs as the same user as the runner, so a deliberately malicious row can still rewrite the file after the runner's last write if it escapes its process group, and can open an ancestor's stdout under `/proc` to write into the job log while it runs. On `pull_request` runs the runner itself comes from the pull request head, so whoever can write such a row can rewrite the runner. The controls therefore target accidental and output-borne forgery: the path is not exported, records come from the runner's memory after the row's process group is confirmed gone, and a line a row appends is discarded at the next rewrite. A per-record HMAC keyed by a per-run secret held only in runner memory was evaluated and **not adopted**: a key that is never disclosed cannot be verified by the collector, a key revealed after the last row can be read by an escaped same-user process, and the runner holding the key is pull-request-controlled. The checkable integrity property is cross-channel agreement, which the verjson-observability#272 collector must enforce: each record matches its row line (group, command, status, elapsed, budget), the record count equals the logged `command_count`, and any disagreement fails closed. A key-bearing design becomes meaningful only if the records are produced by a process outside the row's user and trust domain, such as a separate job that consumes the log.
4. **Receipt.** Scratch run [Verjson/demo-repository 39066757142](https://github.com/Verjson/demo-repository/actions/runs/39066757142) ran this runner on `gha-general-8` (`self-hosted`, `general`) against stubs for (a), (b), (c), a bare-carriage-return variant, and column-0 `::error::`, indented `::warning::`, and `##[group]` lines. The stored log holds every row line byte-identical to what the runner printed and unmasked, every stub line `| `-prefixed (the carriage-return stub split into three prefixed stored lines, confirming the `ReadLine` split), the runner's own group markers stored as `##[group]` and `##[endgroup]`, and both stop-commands lines stored with the token masked (`::stop-commands::***`, `::***::`). The check run's only annotation is the `::notice::` a later step printed, so no replayed command executed, commands resumed after each block, and no mask persisted; the five JSONL records matched the five row lines.

## Amendment (2026-11-02) — declared budgets also order dispatch

### Context

The runner started rows in manifest order. An `@exclusive` row drained every active sibling before it started, so a slow row placed after one started late and ran alone at the end. In `main` run 40642682859, `platform` took 447 s of wall time for 1202 s of row time on 4 CPUs. Its three slowest rows (130-185 s) sat after the `@exclusive` row at manifest line 54 and started about 213 s in ([verJSON/.github#1971](https://github.com/verJSON/.github/issues/1971)).

### Decision

The runner starts every `@exclusive` row first, in manifest order, and each one completes before the next row starts. It then starts the remaining rows at the available parallelism: rows with a declared `@budget` first, highest budget first, followed by undeclared rows. Rows with equal budgets, and all undeclared rows, keep manifest row order. Budgets are already twice a row's slowest CI measurement, so a declaration ranks the row by cost without a separate timing table. The ranking applies on every event. Enforcement is unchanged: a declared budget still caps a row only when the group budget is set. Before any row starts, the runner checks that the dispatch order names every selected row exactly once, and exits 2 if it does not.

### Consequences

- Replaying run 40642682859's runtime records through the dispatcher, `platform` drops from 446 s to 367 s and `merge-gate` from 105 s to 86 s. The ideal longest-first order would give 365 s and 86 s. `changelog-release-*` cells are unchanged, because each one's single shard row is its long pole.
- Raising or adding a `@budget` now also moves that row earlier, and the pinned declarations in `scripts/actions-ci-groups.test.sh` review both effects at once. A slow row without a declaration starts with the undeclared rows in manifest order, so measured rows above 30 s should keep declaring budgets as item 2 already requires.
- Exclusive rows no longer wait for siblings to drain, because none have started. Runtime records stay in manifest order, and the progress line counts rows in start order.

## Amendment (2026-11-02): the case-selection count lives in one place

Decision item 4 says every caller-contract run makes "exactly 268 case selections". By [verJSON/.github#1974](https://github.com/verJSON/.github/issues/1974) the pinned count had grown to 388 while that sentence stayed unchanged. The authoritative value is `CHANGELOG_CALLER_CONTRACT_CASES` in `scripts/changelog-caller-contract-shard.sh`. Every shard fails if a run's selections drift from it, and `scripts/ci-gate/changelog-caller-contract-shard.test.sh` checks that the four shards partition it. Read the current number there, not from this record. The decided mechanism is unchanged: a fixed, pinned selection count, partitioned across the four `changelog-release-*` cells.

## Amendment (2026-11-05): every group writes runtime records, and hot cases get their own rows

### Context

[verJSON/.github#1999](https://github.com/verJSON/.github/issues/1999) found three gaps in the records from the 2026-10-17 amendment. The `docs` and `locale-collation` groups wrote none. Records are per row, so a row's cost could not be split into its cases without local profiling. The `RELEASE_CALLER_ISOLATION_PART=contract` row took 23 to 32 seconds over 11 hosted runs but declared no budget. Item 2 requires a budget above 30 seconds.

Pull-request runs that uploaded no records were all runs where `shell-test-groups` was skipped: drafts, or changes without heavy paths. No PR run skipped an upload after its rows had run. A failed `platform` cell still uploaded its records (run 41735004728).

### Decision

1. Every step that runs `scripts/actions-ci-group.sh` sets `ACTIONS_CI_RUNTIME_RECORDS` to `runner.temp/actions-ci-runtime-records-<run_id>-<attempt>/<group>.jsonl`. The next step uploads that file `if: always()`, as `actions-ci-runtime-records-<run_id>-<attempt>-<group>`, from a step named `Upload <group> runtime records`. This now covers `docs-contracts` and the `locale-collation` step in `hosted-compatibility-tests`. The collector already finds an artifact by the groups a job's log announces, so it needs no change. `docs-contracts` runs on every pull request, drafts included, so every PR run now uploads at least one records artifact. `scripts/actions-ci-groups.test.sh` checks every group-runner step rather than the matrix job alone.
2. The record schema gets no per-case field. The verjson-observability collector rejects any field it does not know and any `schema_version` other than 1. A new field would make every group's records unreadable until a version 2 lands in both repositories. Instead, a case that is known to dominate its row runs as its own row, with the row's existing part selector. Its record then measures that case alone, under schema 1 and the collector's existing cross-checks. The first such case is the release-caller `allowlist sweep`: locally it took 12.3 of the contract part's 13.7 seconds. It now runs as `RELEASE_CALLER_ISOLATION_PART=allowlist-sweep`. Do not give every case its own row: the Context above measured how that multiplies fixture walks.
3. The sweep row declares `@budget=90`, twice 32 seconds rounded up to 30 seconds. 32 seconds is the slowest hosted run of the contract part that carried the sweep (main run 41921027849), so it bounds the sweep from above. The rest of the contract part took 1.3 seconds locally and stays under the 60-second default. Lower the declaration once hosted records for the sweep row run well under half of it.

### Consequences

- Consumers can now expect a records artifact for `docs` and `locale-collation` wherever the job's log announces the group. The 2026-10-17 amendment's statement that those groups produce no records no longer holds.
- Per-case cost is recorded only for cases that have their own row. A case that becomes a hot spot gets its own part, and the part's partition test pins that it runs once.
