# Canonical CI adopter bootstrap

Use `scripts/bootstrap-canonical-ci.py` to check or converge the organization-facing
contract without adopting Verjson-branded configuration names.

## Owner prerequisites

1. Fork or clone the canonical contract at one reviewed 40-character commit SHA.
2. Register each required GitHub App in the adopting owner account, disable webhooks,
   and install it with the repository selection declared in the manifest. This
   legacy bootstrap supports only all-repository installations; selected-repository
   onboarding requires the complete paginated inventory contract described below.
   GitHub App registration and private-key generation are owner-mediated GitHub UI
   operations; the ordinary REST API cannot replay them idempotently.
3. Enter each App's exact slug, App ID, client ID, installation ID, permissions,
   events, and repository selection in the manifest. The bootstrap validates these
   fields and never modifies or widens an App.
4. Declare every secret's purpose in the manifest. The legacy bootstrap supports the
   explicitly allowlisted organization credential `NODE_AUTH_TOKEN`. Use
   `kind: app_private_key` with the canonical `role` from `apps` for an App key; its
   secret name must be exactly `<role>_PRIVATE_KEY`. Every other name, including an
   alias or renamed private-key-like credential, is rejected before it can be
   reclassified as an organization value. Export each legacy-compatible value under
   the environment-variable name declared by the manifest. Values are consumed only by
   `apply`, through standard input to `gh`, and never appear in the receipt. Do not put
   `AI_REVIEW_APP_PRIVATE_KEY`, `MERGE_APP_PRIVATE_KEY`, or
   `RELEASE_APP_PRIVATE_KEY` in this manifest or export their private keys for this
   command; those roles require the environment-only provisioning path below.
5. Authenticate `gh` as an active owner of the target organization. The token needs
   organization Actions-variable/secret administration and read access to the App
   installation inventory.

Start from `docs/examples/canonical-ci-bootstrap.json`. Replace all sample identities;
do not reuse another organization's App IDs, installation IDs, client IDs, or keys.
The permission maps in that example are the maximum canonical role contracts. Remove
an unused role rather than broadening it.

## Run

`apply` currently rejects any manifest containing generated callers before
performing local or remote writes. Caller delivery is held until the shared
ownership and conflict-safe delivery contract in [#1965](https://github.com/VerJSON/.github/issues/1965)
is implemented. Use `dry-run` or `check` to inspect caller drift; those modes do
not deliver files. A manifest with no callers may still apply its separately
authorized organization settings.

```sh
python3 scripts/bootstrap-canonical-ci.py dry-run adopter.json \
  --workspace /path/to/adopter-worktrees \
  --contract-root /path/to/Verjson-.github \
  --receipt bootstrap-dry-run.json

python3 scripts/bootstrap-canonical-ci.py apply adopter.json \
  --workspace /path/to/adopter-worktrees \
  --contract-root /path/to/Verjson-.github \
  --receipt bootstrap-apply.json

python3 scripts/bootstrap-canonical-ci.py check adopter.json \
  --workspace /path/to/adopter-worktrees \
  --contract-root /path/to/Verjson-.github
```

`dry-run` reads live metadata and generates caller outputs in memory without
applying them or changing remote settings. It does not require secret values.
For a manifest without callers, `apply` updates
drifted variables and uploads declared legacy-compatible opaque secrets. A manifest
with callers is held before any apply effects. `check` requires readable settings
and matching generated bytes. GitHub does not return secret values, so `check`
verifies only secret name and visibility; apply is the value-convergence operation.
A manifest containing an environment-only
App-key name returns `status: provisioning_required` before GitHub or output mutation,
including in `dry-run` and `check`.

An explicit `--receipt` creates a new file and refuses an existing path, including
a symlink. Failed apply before remote effects writes its result to standard output
instead of touching the receipt path. If an apply may have partially changed remote
state, it emits the result to standard output and attempts to create the receipt;
if creation fails, preserve the output for reconciliation. A failed receipt write
may leave an incomplete newly created file and is not proof of rollback.
Dispatched variable or secret writes that report errors have an `uncertain`
status: inspect authoritative state and reconcile before retrying.

## Environment-only App-key roles

The legacy `secrets` map writes organization Actions secrets. `NODE_AUTH_TOKEN` is the
only non-App organization credential supported by this manifest contract. Each App-key
entry must bind its secret name to a declared canonical App role; a missing, undeclared,
or renamed App-key binding is rejected before any GitHub call. The classifier uses only
the exact credential map and role contract, never secret values. The legacy path cannot
provision or validate the storage provenance of `AI_REVIEW_APP_PRIVATE_KEY`,
`MERGE_APP_PRIVATE_KEY`, or `RELEASE_APP_PRIVATE_KEY`, so the script rejects those
canonical role names in every mode. A populated organization secret, inherited key, or
readable secret metadata cannot prove that the key is confined to the caller-owned
environment.

Use the [environment App-key rollout](app-key-environment-rollout.md) for these roles:
provision `ai-review-app`, `merge-app`, or `release-app` with the exact main-only
deployment policy and store the matching private key directly in that repository
environment. The approved path is owner-mediated and remains outside this legacy
organization-secret bootstrap until a provisioning implementation supports the full
environment, policy, and selected-repository contract. Existing organization or
repository copies are migration state and are not deleted or rotated by this change.

Each caller entry names a repository directory beneath `--workspace`, an allowlisted
generator, its arguments excluding the contract SHA, and its output. For changelog
generation, the first argument is the generator mode. Every caller receives the one
top-level immutable `contract_sha`; mutable branches and mixed pins are rejected.

## App roles and trust boundaries

- Review authorization: Checks write, Contents read, Pull requests write, Metadata
  read. It authors head-bound review authorization; it does not merge.
- Terminal merge: Contents write, Pull requests write, Metadata read. Ruleset bypass
  is a separate owner action and is not inferred or configured by this script.
- Release: Contents write and Metadata read. Its ruleset bypass is likewise separate.
- Renovate compatibility: Actions, Checks, Contents, Pull requests, and Commit
  statuses read, plus Metadata read. It has no write permission.
- Dependency supersession: Contents read, Pull requests write, and Metadata read. Its
  private key is delivered only to the exact-repository terminal reconciliation token
 mint; observation continues to use the read-only Renovate compatibility role.

Renovate compatibility and dependency supersession remain on their current
organization-secret contract until an explicit custody decision changes those roles.
Their entries use the same exact role-derived App-key names and remain eligible for
this legacy path.

Dependency supersession adopters provide organization variable
`DEPENDENCY_SUPERSESSION_APP_CLIENT_ID` and secret
`DEPENDENCY_SUPERSESSION_APP_PRIVATE_KEY`. Do not create
`DEPENDENCY_SUPERSESSION_WRITE_ENABLED` during initial bootstrap: its absence keeps the
terminal reconciler observe-only until a reviewed disposable canary explicitly enables
the rollout gate.

All canonical role Apps subscribe to no webhook events and this bootstrap supports
only all-repository installations, whose scope is completely observable in the
organization installation inventory. If an installation reports a different event,
permission, identity, suspension, or repository selection, bootstrap stops. A future
selected-repository mode requires a new manifest allowlist and paginated exact
repository-membership validation; it must not reuse this mode's evidence.
Do not interpret an incomplete selected-repository inventory as proof that an
environment key has been provisioned for the required cohort.

## Rollback and legacy coexistence

For organization-only changes, reapply the prior reviewed manifest and immutable
contract SHA. Caller delivery remains held; no local rollback is attempted. Keep legacy
organization-branded variables while immutable historical callers still reference
them; the bootstrap neither creates nor deletes those names. Secret rollback requires supplying
the previous secret value. App key revocation/rotation and ruleset bypass removal are
manual owner actions and should be recorded with the run receipt.
